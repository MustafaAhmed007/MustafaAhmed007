# Authority System — GitHub Profile v2

## Objective

The GitHub profile is treated as a technical authority surface: a visitor should understand identity, specialization, flagship systems, proof, engineering method, and opportunity path without having to decode a résumé.

## Perception architecture

```text
IDENTITY
  ↓
POSITIONING
  ↓
FLAGSHIP SYSTEMS
  ↓
SOURCE CODE
  ↓
ARCHITECTURE
  ↓
TESTS / CI / VALIDATION
  ↓
DEMO / OUTCOME
  ↓
TRUST
  ↓
OPPORTUNITY
```

The visual layer creates the first impression. The repositories create the second impression. Verification and inspectable implementation create the third.

## Authority rules

### 1. Systems over slogans

Use concise positioning, then immediately show real systems. Avoid long lists of generic capabilities without a corresponding repository, artifact, demo, benchmark, or case study.

### 2. Evidence over vanity

Do not publish unsupported numbers, fabricated clients, invented users, or unverified performance claims. A smaller set of inspectable systems is more defensible than a larger claim list.

### 3. Technical depth without visual noise

The aesthetic target is **AI research lab + engineering command center**, not a gaming terminal. Use restrained motion, readable typography, strong hierarchy, and a small number of deliberate visual signals.

### 4. Public-first proof

The flagship registry contains only repositories that are public and inspectable. Private projects may inform future case studies, but they are not presented as public proof.

### 5. One narrative

The flagship sequence should communicate a coherent capability arc:

```text
AI / RAG
  ↓
AGENTS / AUTHORITY
  ↓
DEVELOPER INFRASTRUCTURE
  ↓
META-SYSTEM / PROFILE ENGINEERING
```

## Proof ladder

Every important claim should be able to move through this ladder:

```text
CLAIM
 ↓
PUBLIC REPOSITORY
 ↓
ARCHITECTURE
 ↓
RUNNABLE PATH
 ↓
TESTS
 ↓
CI
 ↓
DEMO / DEPLOYMENT
 ↓
MEASURED OUTCOME
```

Not every project will reach every level immediately. The profile must not imply a level that has not been achieved.

```text
10-SECOND VISIT
      ↓

      ↓
```

The README therefore prioritizes identity and flagship systems before explaining the machinery behind the README itself.

## Monetization / opportunity path

The profile is designed to convert technical credibility into:

- AI engineering opportunities
- systems architecture engagements
- automation projects
- consulting
- product engineering work
- open-source collaborations

The system does not promise outcomes it cannot prove. Its job is to reduce uncertainty for a technically sophisticated visitor.

## Maintenance rule

Whenever a flagship repository changes materially:

1. verify the public repository is still accessible;
2. update its profile description only if the implementation changed;
3. preserve evidence-first language;
4. run the profile quality gate;
5. review the README as a first-time technical visitor;
6. remove stale claims before adding new ones.
